## t-6 抢 ack 根因定谳（09-13 16:50 取证，HS 084649 请求）

**现场**：t-7 交付信 `20260913083051-39603a62-hs` 落盘 16:30:51.297，**450ms 后**被改成 acked（acked_at=16:30:51，mtime=16:30:51.747），`handled_log=None`；HS 侧后续 check 只见 unread=0/pending=0。

**根因两条（都已定位到行/进程）**：

1. **`mailbox_wait` 投递即 ack**：`server.py:155-170` 的长轮询 = `list_messages(status="pending")`
   → 命中即 `check(mark=True)`（= 直接写 acked）→ 返回调用方；轮询间隔 **0.5s**。
   铁证：hermes `agent.log` 16:30:51,749 `[session 20260913_160420_3293da0b] mailbox_wait completed (11.18s, 4155 chars)`
   ——与 ack 落盘**同毫秒**（0.5s 轮询节奏解释 450ms 延迟）。同批信件 acked_at 与各会话 wait 完成时刻逐条对上
   （16:35:49 / 16:37:20 / 16:38:17）。⇒ **抢 ack 的是收件人侧自己的长轮询会话**，不是 ZC drain、不是 wake 脚本。
   风险面：唤醒侧**并发拉起多个短命会话**（同一分钟 3293da0b / 20e92f52 / 5e9a5291 / 39fa9aaa / 7c43e221 都在
   check/wait）→ 惊群抢认领，谁先谁 ack；认领会话若随后夭折（回合取消/进程死/上下文丢），信就停在 acked 无人读过。
2. **长驻 MCP server 持旧代码**：`python -m agent_mailbox.server` PID 79194 启动于 **2026-09-11 20:06:31**，
   而 `handled_log` 提交时间是 **09-12 02:17**（4624904）⇒ 该进程内存里是**无 handled_log 的旧代码**，
   它做的每一次 ack 都不会留痕。这修正了此前「旧版 store 副本」的表述：**不是磁盘上有旧副本，是长驻进程钉住旧代码**
   （磁盘 working copy 09-13 16:15 已含 handled_log）。推论：MCP server / watcher(98980) / web(8645,8646) 等
   长驻进程在 store 代码更新后**必须重启**才生效；否则 handled_log 审计、reap 等新行为全部不可见。

**量化（全库 rglob，833 件）**：acked 226 件（>1h 206 / >24h 205 / 中位 91.8h / 最老 8.7 天）；
