# v0.8.x 用户旅程与路线图建议

2026-09-30。本文是讨论提案，不是已实现能力、发版承诺或新增 PRD 正典。已批准的员工侧信箱单独落实。

## 判断

agent-mailbox 应先让一个普通人管理已有 AI 员工，围绕项目共享资料、沟通、派工、交付与验收。组织与 ERP 能力建立在可靠的项目闭环上。发现入口、成功登录、可受管执行、曾成功执行是四个不同事实。

本轮查验：Mac 上登记了 18 个入口（9 CLI、9 app），不代表 18 个都能受管执行。当前执行适配仅覆盖 Codex/Claude CLI，桌面 app 不能因已安装就声称会自动响应。Codex 曾跑通真实任务；Claude 最小认证测试成功，但前一次完整项目协作超时，仍需真正双员工闭环验证。当前主要是只读工作，代码修改、隔离工作区和产物合并不能算已完成能力。

## 小白路径

发现员工 → 解决连接问题 → 创建项目并选文件夹 → 邀请员工 → 加入必要资料 → 发消息或明确派任务 → 看进度与产物 → human 验收。

默认不要求画流程、不要求填写模型 key、不要求逐个配置 MCP。界面引导应使用“缺登录／已登录但适配器连接失败／当前不支持自动执行／设备离线”等真实原因，给出对应下一步。

| 阶段 | 需要完善的体验 | 验收证据 |
|---|---|---|
| 首次运行 | 自带依赖；一条安全演示任务；空状态引导；发现但不支持入口明确标记 | 新用户无需终端或编辑 MCP，独立得到首个结果；模型调用前明确告知 |
| 员工管理 | 将同一产品的 app/CLI 显示为关联入口，保持会话与权限边界；能力筛选与连接修复 | 不重复计算员工；选派时只给合适且可执行的入口 |
| 项目首页 | 当前目标、下一步、待验收、阻塞、最近成果；把聊天/任务/资料分开 | human 能立即判断谁负责、在等谁、结果在哪 |
| 消息与任务 | 普通沟通无自动派工；明确工作请求绑定任务；送达/运行/待验收/验收分开 | 回信不能把任务自动改为完成；失败原因可追溯 |
| 升级恢复 | 应用与数据分离，升级备份、迁移验证、失败恢复，运行任务安全停点 | 员工、授权、项目、任务和历史无需重配；当前本地替换已验证，不等于用户自助更新已实现 |
| 系统覆盖 | Mac/Windows/Linux 各自安装包和原生验证；Ubuntu 无桌面节点 | 不把 Mac 构建成功外推到 Windows/Linux |

## 工作流程

先提供可选模板，不先上自由画布：

1. 单人任务：human 定义目标与验收 → 员工执行 → 提交产物 → human 验收。
2. 制作与评审：A 提方案/产物 → B 独立评审 → A 修订 → human 验收。当前阶段可先验证只读分析与评审。
3. 调研到决策：研究员带来源交付 → 负责人归纳 → human 拍板 → 正典维护者更新 PRD。

每个任务必须绑定责任人、输入资料版本、预期产物、验收条件、依赖和可用权限。依赖未完成不执行；失败后显示“重试本步骤／换员工／人工处理”，有副作用的操作不盲目重跑。会修改代码的任务先补独立 worktree、diff、冲突处理与合并授权，再开放执行。拖员工进项目表示成员关系；选择任务执行者表示分工；拖员工不应偷偷触发模型。

subagent 默认是员工内部助手，由父员工提交正式交付与邮件。现有凭证绑定父执行会话并不证明内部作者身份；不要在 UI 假称已杜绝 subagent 冒用。未来需要委派身份、子任务记录和受限权限。

## 七件套如何呈现与更新

现有资源登记读取实时文本文件，没有固定版本快照、审批状态、过期检测、跨设备自动复制。下一步建议“项目资料”作为统一入口，普通用户看预览、用途、维护人、更新时间、状态；高级详情才看 commit、hash、索引与来源。

| 项目资料 | 真相来源 | 呈现与更新规则 |
|---|---|---|
| PRD | 已批准的 Git 文档 | 正典与提案分开；改动评审后更新，保留差异与决策来源 |
| AOCI-Code（用户所称 aico-code，命名仍需核对） | 对应代码版本的仓库认知索引 | 显示覆盖范围、有效性、源 commit；索引失效显式标记，不能替代源码证据 |
| archify | 架构文档与可预览图 | 图与源文件一起登记，记录生成依据；代码变更后提示复核 |
| graft | 项目启用的工具及其输出 | 区分可执行工具与生成资料；缓存不当正典，输出绑定来源版本 |
| CodeGraph | 指定源码版本派生的图 | 提供查询入口与更新时间；按需查询，不把全图塞进每次模型上下文 |
| todo-list | 同一个任务数据库 | 看板/列表是同一数据的视图，避免另维护一份 Markdown 真相 |
| daily-update | 任务事件、交付、阻塞、人工决定 | 自动生成可核对的草稿；链接证据，不能把模型摘要写成已验收事实 |

共享的是授权的资料版本与工具能力，不是所有人的登录信息。任务开始固定输入版本；资料有新版时提示“继续旧版／升级输入并重跑受影响步骤”。Git 适合文本与源码，文件存储适合产物，数据库适合任务与事件；不必所有内容都 Git，也不必引入向量数据库。跨设备以资源清单、版本和内容校验取资料，本地路径映射各自维护。

工作日志应直接从真实事件生成：分派、开始、审批、失败、交付、评审、验收、资料更新与人工备注。普通日志不是防篡改审计；审计级签名/追加链可后续做。已有项目笔记是第一层 memory，向量检索等资料规模确实需要再加。

## 跨设备

IP 只解决“地址在哪”，不能解决身份、连接、授权、环境、文件版本、离线与恢复。建议产品化成向导：

1. 主控生成一次性、有过期时间、限定项目的邀请。
2. Ubuntu 安装节点并在本机登录自己的 agent；接受配对，核对设备身份。
3. 选择连接方式：LAN 私有 HTTPS、私有网络或 SSH 隧道；不默认暴露 human 管理入口。
4. 映射该设备项目目录，核验依赖、Git/资料版本、执行能力、读写权限。
5. 先检查连接和读取，再经用户明确发起低成本测试任务。
6. 显示连接、排队、运行、回执状态；撤销设备立即停止后续授权。

当前已有私有 HTTPS、证书指纹固定、一次性配对、项目范围与目录映射、远端运行器和终态回执 outbox，主要是命令行操作；香港/美国真实 Ubuntu 联调尚未完成。配对不会自动传输代码、资源或供应商登录。断网后的回执重投不等于任务可安全自动重跑。

Mac 首先可作为唯一主控，香港/美国作为各有本地工作区与凭证的节点。需要全天运行时，再迁移主控到常在线 Ubuntu；前提是数据与主控身份迁移、唯一队列所有者和恢复经过验证。Mac 休眠的影响必须显式显示，不能许诺仍可靠派单。暂不做多主控抢同一队列。

Tailscale 可以参考设备登录、私有连通体验，但网络接通后仍需 mailbox 自己的项目授权与文件一致性：[官方设备指南](https://tailscale.com/docs/features/access-control/device-management/how-to/set-up)。

## 建议优先级（版本号为讨论顺序）

| 阶段 | 核心成果 | 放行条件 |
|---|---|---|
| v0.8.0 收口 | 两名支持员工的单机真实闭环、信箱与失败可见、安装升级保留数据 | human 发起 → A 分析 → B 评审 → 产物 → human 验收；重启不丢记录 |
| v0.8.1 | 新手向导、入口关联、优先补用户已有员工适配；多操作系统安装诊断 | 新手可独立上手；每个声称支持的适配都跑真实验收 |
| v0.8.2 | 版本化资料、工作日志、三种流程模板；写代码前补隔离与 diff 评审 | 固定版本输入、可追溯交付、明确人工合并，无双份任务真相 |
| v0.8.3 | LAN/香港/美国节点向导、连接诊断、离线恢复与主控迁移 | 真实两设备、Ubuntu、断网/重启/撤权验证 |
| v0.9+ | 成本、三个指标、负责人招募/考核/预算、dsh-devices 接口 | API 受管调用成本可归因；订阅 app 或不可观测调用显示未知；后续再考虑 ERP |

维护性升级与首个闭环优先于新增员工数、流动画布和企业功能。后续版本需依照验收调整顺序，不承诺日期。
