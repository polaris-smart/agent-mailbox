# v0.8.0 workbench implementation

Status: implementation authorized by the human on 2026-09-30. This document records the scoped implementation and evidence; it does not overwrite the v0.7.6 PRD or claim a release.

## Product contract

agent-mailbox remains the product name and keeps its existing MCP entry point. A new human workbench lets an owner select a project, discover supported existing employees, dispatch work, inspect approvals and results, and keep project knowledge. The application itself needs no model key. Supported employees use their existing provider authentication. Their managed sessions do not attach to arbitrary open desktop conversations.

Employee identities, project membership, tasks, results, logs and knowledge are durable product data. Execution sessions are replaceable associations. Message transport, execution completion and owner acceptance are distinct facts. Only owner acceptance makes an executed task done. Restarting an interrupted execution never silently repeats its side effects.

## Foundation decision

The engineering spike actually installed and started isolated Paperclip 2026.916.1 and AionCore 0.2.2, without model calls or service installation. Paperclip served its frontend and health API, but the measured install including its local runtime was approximately 1.6 GiB. AionCore's 34.5 MiB archive served health but no frontend, and warned about missing managed Node assets. Fixed acpx 0.19.3 installed and exported its runtime, with approximately 43 MiB dependencies before Node and adapters. Archived evidence: [foundation smoke](../evidence/v080/foundation.md).

Choose the existing Python product/compatibility layer plus fixed acpx runtime. This is based on installation and migration boundaries, not loyalty to the old architecture. SQLite holds the new workbench domain; the legacy mailbox continues to work without rewriting old identities or global MCP configuration. MIT remains the product license, with upstream notices retained for distributed components.

## Modules and owned seams

| Module | Responsibility |
|---|---|
| `workbench_store.py` | Projects, employee membership, atomic task claims, results, permissions, logs, knowledge and SQLite backup |
| `runtime_bridge/` | Fixed ACP/acpx component; structured process events, scoped sessions, permission requests, cancellation |
| `workbench_runtime.py` | Read-only discovery and explicit runtime provisioning; Python bridge consumer |
| `workbench_engine.py` | Durable queue scheduling and lifecycle; connects bridge events to store and owner decisions |
| `workspace_mcp.py` | Employee/project-scoped context, knowledge and team messaging; no global host config edits |
| `workbench.py` | Authenticated loopback HTTP API and launcher |
| `workbench_assets/` | Accessible bilingual project UI; authentic states, no fabricated live data |
| `workbench_fleet.py` | Optional paired LAN node transport, certificate pinning, project mappings and scoped execution |
| Packaging and acceptance | Clickable local application artifacts, bundled runtime, baseline regression and real process tests |

Local owner API → store transaction → worker claim → managed bridge → employee session → structured result → review → human acceptance. Every step has an actual consumer. Knowledge and tools are injected into managed sessions, rather than installed into the human's global configuration.

## API and states

Workbench APIs are namespaced `/api/workbench/`. Owner access uses a bearer token bootstrapped by URL fragment, cleared from browser history and stored in session storage. Cross-origin requests and untrusted Host headers are rejected. The default listener is loopback. LAN devices use a separate explicitly enabled TLS listener with an expiring single-use invite and per-device credentials. Device credentials cannot call owner APIs.

Tasks: `queued → starting → running ↔ waiting_approval → review → done`. Failure, cancellation and interruption are explicit. A process exit alone is insufficient for success; a valid terminal result and nonempty output are required. Cancellation is a request until execution has actually stopped. Permission decisions cannot apply to an expired run. A claim is atomic across competing workers. Exactly-once external side effects are not promised; uncertain execution requires human action.

ACP bridge protocol is version 1 NDJSON. Run requests include stable `run_id`, managed `session_id`, supported agent kind, prompt, trusted project cwd, permission mode, deadlines and session MCP servers. Output includes actual `started`, structured events, permission requests, session association and exactly one terminal `result`. No shell interpretation or automatic full-access fallback. Cwd is an execution scope, not an OS sandbox guarantee.

Knowledge has source, project and timestamps. Human-maintained facts stay distinct from agent-proposed notes. Source files remain authoritative and vector indexes, if added later, are rebuildable. Only explicitly registered resources can be read outside the selected project; credential files are excluded. Shared knowledge is filtered by project membership.

## Verification gates

- Legacy baseline before edits: 557 passed, 1 skipped; 22 existing sampling deprecation warnings.
- Concurrent claims, project isolation, permission expiry, restart recovery, searches and backup restore must have meaningful tests.
- Real bridge subprocess tests verify protocol, permissions, cancellation, timeout and failed resume without model costs.
- Authenticated HTTP tests cover the complete project/employee/task/review path, invalid input, token isolation and visible errors.
- Browser validation must operate the real API and show first-use, live task details and both languages; screenshots are evidence, not a substitute for execution tests.
- Two isolated node processes must prove scoped pairing, routing, path mapping, receipts and rejection of unauthorized owner operations. Same-host simulation must not be described as two physical devices.
- A packaged artifact must open the workbench with isolated state and include runtime assets; no release/tag/push or production service replacement is authorized in this task.
